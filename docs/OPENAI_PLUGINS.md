## What a plugin is

The current directory covers ChatGPT and Codex. A plugin may contain Agent Skills, an MCP connection, or both. A skill describes a repeatable workflow; the MCP server supplies live data, authentication, authorization, and actions. Custom UI is optional. The Scio use case can therefore use **one focused skill plus a remote MCP server**, with no code executed from the plugin ZIP in ordinary ChatGPT. This is an application of the [architecture](https://developers.openai.com/plugins/concepts/plugins), [MCP](https://developers.openai.com/plugins/concepts/mcp-server), and [skills](https://developers.openai.com/plugins/build/skills) guides, not a claim that the existing Scio endpoint is ready.

Start from a user goal and expose only the tools needed for it. For Scio's initial package, the proposed goal is search and source-backed reading where access permits. Contribution and moderation tools need a separate authorization and review decision. Tool names, descriptions, schemas, results, annotations, and server instructions influence tool choice; a skill cannot hide an unsafe or irrelevant advertised tool. Sources: [plan use cases](https://developers.openai.com/plugins/plan/use-case), [define tools](https://developers.openai.com/plugins/plan/tools), [build MCP](https://developers.openai.com/plugins/build/mcp-server), [optimize metadata](https://developers.openai.com/plugins/guides/optimize-metadata).

## Package and supported runtime

The portable layout uses root `plugin.json` with the Agent Plugins schema, root `mcp.json` for the remote server, and `skills/<name>/SKILL.md`. The portable host discovers skills in `skills/` without a manifest `skills` field. A remote MCP entry uses `type: "streamable-http"` and an HTTPS URL. OpenAI presentation and review fields belong under `extensions.com.openai` in `plugin.json`. The older `.codex-plugin/plugin.json` layout is supported as a compatibility format, but its `.mcp.json` is a different format and cannot simply be renamed. Source: [package guide](https://developers.openai.com/plugins/build/plugins).

The package guide discusses optional hooks and app references in some local plugin contexts. **The current public submission guide explicitly excludes ZIPs with lifecycle hooks or `apps`/`.app.json` references.** This resolves the apparent difference between general package support and public submission support. Ordinary ChatGPT also does not execute the old companion plugin's local Python bridge. Sources: [package guide](https://developers.openai.com/plugins/build/plugins), [submission guide](https://developers.openai.com/plugins/deploy/submission), [Claude migration guide](https://developers.openai.com/plugins/guides/submit-claude-plugin).

Only one MCP server can be connected per public plugin, even though a package can declare multiple. The initial ZIP must already contain an MCP server if the intended plugin uses one; a skills-only listing cannot later gain an MCP server through the current update flow. Source: [submission guide](https://developers.openai.com/plugins/deploy/submission).

## MCP server contract

Production MCP needs a stable, public HTTPS Streamable HTTP endpoint. No custom UI is required. Each tool should have an action-oriented name, title, use-case description, explicit input schema, an output schema when returning structured data, accurate safety annotations, and server-side authorization. Put model-readable facts in `structuredContent` or `content`; do not put credentials in tool responses. Server `instructions` can give shared workflow guidance; OpenAI says to put key points in the first 512 characters. Sources: [build MCP](https://developers.openai.com/plugins/build/mcp-server), [testing](https://developers.openai.com/plugins/deploy/connect-chatgpt).

For final remote MCP submission, every exposed tool needs explicit `readOnlyHint`, `openWorldHint`, and `destructiveHint`. The scan reads the actual server metadata: prose in the submission cannot override a wrong server annotation. `openWorldHint` can be true even for a read-only tool when it reaches open-ended public data. **Official-page conflict:** the [current guidelines](https://developers.openai.com/plugins/plugin-guidelines) say annotation justifications are no longer required, but the [submission error reference](https://developers.openai.com/plugins/deploy/submission-errors) still lists a `justification_required` check. Keep concise rationale available, and verify what the portal currently enforces before submission. Sources: [review requirements](https://developers.openai.com/plugins/deploy/app-review), [metadata guide](https://developers.openai.com/plugins/guides/optimize-metadata).

## Authentication and user data

Anonymous read-only operation is permitted when the service actually supports it. Customer-specific data or writes should use authentication. For authenticated MCP, OpenAI expects OAuth 2.1 conforming to MCP authorization: protected-resource metadata, authorization-server discovery, a `resource` parameter, a supported client identification/registration path (CIMD, DCR, or predefined client), PKCE, per-tool security schemes, and token checks on the server. An unauthorized request should provide `WWW-Authenticate`; an MCP tool can also return a `mcp/www_authenticate` challenge for linking. Existing Scio `sk_` keys are **not** a user-facing ChatGPT OAuth sign-in flow. Source: [authentication](https://developers.openai.com/plugins/build/auth).

The guidelines prohibit collecting authentication secrets such as API keys, passwords, and one-time codes through plugin interactions. Use a dedicated OAuth path for account access; do not expose an API key in a model-visible registration result or ask the user to paste it into chat. For OAuth review, use a dedicated demo identity and sample data, with reviewer credentials entered privately in the portal, outside the ZIP. Sources: [plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines), [submission](https://developers.openai.com/plugins/deploy/submission), [security and privacy](https://developers.openai.com/plugins/guides/security-privacy).

OpenAI's [Claude migration guide](https://developers.openai.com/plugins/guides/submit-claude-plugin) adds a workspace-domain consideration for OAuth: expose a UserInfo endpoint with verified email and advertise `openid` and `email` when that feature applies. Recheck the [authentication guide](https://developers.openai.com/plugins/build/auth) before implementing; do not infer that a legacy agent key provides this.

The authentication guide also describes optional multi-account identification: an authenticated read-only profile tool marked `_meta["openai/profile"]: true`, returning a stable opaque profile ID in `structuredContent`. Multiple accounts can connect without it, but the tool helps users distinguish and reconnect profiles. OpenAI says ChatGPT cannot present custom API keys or use machine-to-machine client-credentials grants as this MCP sign-in path. Source: [authentication](https://developers.openai.com/plugins/build/auth).

## Listing and public review

The [submission error reference](https://developers.openai.com/plugins/deploy/submission-errors) is the most precise current field checklist: package name at most 64 characters, semantic version, display name at most 30, short description at most 30, long description at most 4,000, developer name at most 80, at most 20 capabilities, and at most three unique starter prompts of at most 128 characters each. Starter prompts cannot include MCP server `@mentions`. Remote MCP listing requires HTTPS website, support, privacy, and terms URLs. The privacy policy must describe data categories, purposes, recipients, retention, and user controls. Source: [guidelines](https://developers.openai.com/plugins/plugin-guidelines).

The public listing requires a square `logo` and `composerIcon` in the ZIP. PNG, JPEG, WebP, and SVG are supported; each image is at most 5 MiB, and dimensions must be at least 48 × 48 pixels (raster images at most 4,096 × 4,096). Asset references start with `./` and stay inside the plugin root. The ZIP itself must be valid, no larger than 100 MB compressed, and contain one unambiguous plugin root. Source: [submission errors](https://developers.openai.com/plugins/deploy/submission-errors).

Remote MCP submission also requires a production endpoint, successful current tool scan, domain verification, release notes, an accessible demonstration video, **exactly five positive and three negative cases**, and reviewer-ready credentials if OAuth is used. Screenshots are allowed only for custom UI; if included, there must be one per starter prompt at the specified dimensions. The challenge token goes as exact plain text at the portal-provided `https://<eligible-host>/.well-known/openai-apps-challenge`. Source: [submission](https://developers.openai.com/plugins/deploy/submission), [submission errors](https://developers.openai.com/plugins/deploy/submission-errors).

The publisher needs a verified individual/business identity and the needed Apps Management permissions. A project with EU data residency currently cannot submit an MCP plugin for review, according to the remote MCP review page. Approval and publication are separate portal steps. Hosted MCP changes are scanned after publication; changes to package metadata or skills require a new ZIP. Sources: [remote MCP review](https://developers.openai.com/plugins/deploy/app-review), [submission](https://developers.openai.com/plugins/deploy/submission).

Listing text must state the real capability plainly. Do not use comparative hype, claims about pricing or promotions, broad tool triggers, or instructions to call Scio for unrelated questions. The guidelines disallow plugins that are incomplete demo experiences. Sources: [guidelines](https://developers.openai.com/plugins/plugin-guidelines), [metadata guide](https://developers.openai.com/plugins/guides/optimize-metadata).

## Testing sequence

1. Test the public HTTPS MCP endpoint directly with MCP Inspector: `tools/list`, tool schemas, anonymous and authenticated calls, empty results, invalid inputs, missing IDs, rate/access errors, and confirmation behavior. Verify that model-readable results contain source links and honest coverage limits for the intended Scio workflow. Source: [connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt).
2. In ChatGPT developer mode, add the MCP connection, inspect the discovered metadata, then exercise direct, indirect, follow-up, write-boundary, and non-trigger prompts. Record selected tools, arguments, output, errors, and confirmations. After metadata changes, refresh the connection and start a new conversation. Source: [connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt).
3. Install the full package and test skill activation, skill non-activation, and cross-surface behavior. Keep a labeled prompt set for regressions. Source: [build skills](https://developers.openai.com/plugins/build/skills), [connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt), [metadata guide](https://developers.openai.com/plugins/guides/optimize-metadata).
4. Upload only when the remote integration and review materials are real. The portal performs separate metadata/skill checks and MCP scan. Resolve reported errors, enter private reviewer credentials in the portal, submit the draft, await review, then publish only with the owner's authorization. Source: [submission](https://developers.openai.com/plugins/deploy/submission).

Developer mode can use a tunnel for testing, but the submitted MCP endpoint must be public and stable. Developer mode availability can depend on account/workspace policy. These notes do not establish that this repository has been installed in ChatGPT, deployed, submitted, reviewed, or approved. Source: [connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt).

## Scio decisions to discuss before implementation

These are inferences from the official requirements and the local project brief, not findings from an OpenAI review:

- Should the first endpoint expose only public search and source inspection, with OAuth added later for private reads? The answer depends on real anonymous MCP behavior and Scio access policy.
- Which exact read tools and server annotations will the dedicated endpoint advertise? The final review cases must match `tools/list` at the deployed URL.
- How will Scio issue OAuth tokens for ChatGPT while preserving existing agent keys and clients? This belongs in the platform server; this package can only reference that endpoint.
- Which source URLs and coverage fields will the returned result contain, so the skill can cite evidence accurately without inventing articles or implying universal coverage?

No Scio server behavior or OpenAI portal status was validated by this documentation pass.

## Other documented capabilities and exclusions

The [MCP build guide](https://developers.openai.com/plugins/build/mcp-server) can import server-hosted skills through `capabilities.extensions["io.modelcontextprotocol/skills"]`; `skills/list`, `skills/get`, and `resources/read` provide a **static submission-time snapshot**, subject to file and size limits. This is an alternative to bundling the Scio skill in the ZIP, not required for the proposed simple package. The guide also describes standard `search` and `fetch` schemas for company knowledge eligibility; that is a separate feature decision.

The [skill build guide](https://developers.openai.com/plugins/build/skills) says a skill that requires an MCP server should declare it in `agents/openai.yaml`. Its packaging example uses legacy-style manifest fields, while the [portable package guide](https://developers.openai.com/plugins/build/plugins) says root `skills/` is discovered without a `skills` field. Treat this as a documentation ambiguity for the portable format and verify the combined package in the actual host/portal before calling it submission-ready.

[MCP Apps UI](https://developers.openai.com/plugins/build/chatgpt-ui), [UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines), [OpenAI UI extensions](https://developers.openai.com/plugins/build/extensions), and the [UI reference](https://developers.openai.com/plugins/reference) describe server-hosted iframe widgets, display modes, component state, CSP, and optional ChatGPT surfaces. No UI is needed to return text and structured search results. If UI is added later, keep headless tool results useful and put authoritative state on the server.

[MCP Events](https://developers.openai.com/plugins/build/mcp-events) require MCP 2.0 (`2026-07-28`), event discovery/subscriptions and signed HTTPS webhook delivery. They are supported on specific Work/Cloud surfaces and introduce background behavior. The proposed Scio search package does not need them.

The [restaurant reservation](https://developers.openai.com/plugins/guides/restaurant-reservation-conversion-spec), [local-services quote](https://developers.openai.com/plugins/guides/local-services-request-quote-conversion-spec), and [product checkout](https://developers.openai.com/plugins/guides/product-checkout-conversion-spec) contracts are beta partner conversion integrations with prescribed tool/widget names and feed formats. The [checkout reference](https://developers.openai.com/plugins/build/monetization) covers physical-goods checkout and a limited payment-sheet beta. They do not apply to Scio search; do not introduce checkout promises or code from them.
