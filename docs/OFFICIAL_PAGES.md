# Official OpenAI Plugins: page-by-page review

All **29 pages named by the owner** were reviewed on **2026-10-02**, starting from [Plugins](https://developers.openai.com/plugins). This is a paraphrased findings index, not a copy of those pages. The official page is authoritative. The site also links to external specifications and examples; those external sites were not opened for this review.

For the 2026-10-03 full OAuth package and current requirement status, see [OPENAI_REQUIREMENTS.md](OPENAI_REQUIREMENTS.md). This page remains the original 29-page snapshot.

## Findings from every requested page

1. [Quickstart](https://developers.openai.com/plugins/quickstart): demonstrates a personal MCP plugin with a public anonymous `roll_dice` tool. It connects the endpoint in developer mode, installs the personal plugin, then invokes it in ChatGPT Work. It explicitly asks for realistic, invalid, and non-trigger tests. This is a development path, not public approval.
2. [Plugin architecture](https://developers.openai.com/plugins/concepts/plugins): four useful shapes are skills only, MCP only, both, and MCP with UI. The directory is shared by ChatGPT and Codex, but capability support varies by surface. Web installation does not deploy local hook scripts. Text and structured results work without UI.
3. [Skills concept](https://developers.openai.com/plugins/concepts/skills): skill metadata determines when the model considers it; the body contains workflow steps and output rules. A skill can combine search and fetch, handle incomplete results, and prevent inference beyond data. Live data and authorization belong to the MCP server.
4. [MCP concept](https://developers.openai.com/plugins/concepts/mcp-server): MCP can expose tools, resources, prompts, and server instructions. Plugins mainly use tools. Production transport is stable HTTPS Streamable HTTP. Returned text/structured content must be enough for a headless answer.
5. [Brainstorm use cases](https://developers.openai.com/plugins/plan/use-case): inventory direct and indirect user goals, expected result, context, safety boundary, and support decision before deriving tools. Exclusions should be deliberate and reflected in listing, refusal behavior, and tests. A narrow implementation must have narrow public positioning.
6. [Define tools](https://developers.openai.com/plugins/plan/tools): design user-facing actions rather than mirroring an internal API. Separate reads and writes with different permissions. For each tool record name, title, schemas, authorization, side effects, failure behavior, and accurate hints. Return stable follow-up IDs, never secrets.
7. [Build MCP server](https://developers.openai.com/plugins/build/mcp-server): tool metadata, `outputSchema` for structured results, server instructions, and authorization are part of the contract. The first 512 characters of server instructions matter most. Server-hosted skills can be imported through the draft skills extension, but are static snapshots at scan time. It also mentions standard `search`/`fetch` schemas for company knowledge eligibility; that is separate from ordinary Scio search.
8. [Add UI](https://developers.openai.com/plugins/build/chatgpt-ui): new UI uses MCP Apps `_meta.ui.resourceUri`, `text/html;profile=mcp-app` resources, and a JSON-RPC bridge over `postMessage`. ChatGPT aliases under `window.openai` are optional. Keep data tools useful without rendering; separate data and render tools when the component would otherwise remount repeatedly. Server owns business state, component owns temporary presentation state, and CSP declares exact network origins. No UI is necessary for the first Scio workflow.
9. [MCP Events](https://developers.openai.com/plugins/build/mcp-events): Work/Cloud-specific event subscriptions require MCP 2.0 (`2026-07-28`), `server/discover`, `events/list`, `events/subscribe`, and `events/unsubscribe`. Delivery uses verified public HTTPS callbacks and signed Standard Webhooks, with stored subscriptions, access rechecks, retry rules, and payload limits. This is background behavior and outside the proposed search scope.
10. [Extensions](https://developers.openai.com/plugins/build/extensions): optional ChatGPT entry points include sidebar apps, conversation panels, plugin settings, file viewers, deep links, model/app context, composer mentions, rich forms, and onboarding. Web rollout and desktop availability differ; composer mentions are desktop only. None is required for a simple MCP plus skill package.
11. [Authentication](https://developers.openai.com/plugins/build/auth): anonymous reads may be supported, while private data and user actions need OAuth 2.1. The page details protected-resource and authorization-server metadata, `resource` propagation, PKCE S256, CIMD/DCR/predefined client paths, token signature/issuer/audience/expiry/scope checks, per-tool `securitySchemes`, and `mcp/www_authenticate` to trigger linking. ChatGPT cannot present custom API keys as MCP login. Its optional profile tool has a stable opaque ID and `_meta["openai/profile"]: true` for multiple connected accounts.
12. [Build skills](https://developers.openai.com/plugins/build/skills): `SKILL.md` needs name and description frontmatter; instructions specify inputs, steps, outputs, limits, and when to ask/stop. Test direct and indirect activation, missing input, non-trigger and edge cases. The page says MCP-dependent skills declare `agents/openai.yaml`; verify how this interacts with the portable package guide before claiming a ZIP valid.
13. [Package](https://developers.openai.com/plugins/build/plugins): root portable `plugin.json` and `mcp.json` use Agent Plugins schemas; `skills/` is automatically discovered by portable hosts. `mcp.json` remote entries declare `type: "streamable-http"`. The page also explains legacy `.codex-plugin/plugin.json`, local marketplaces and workspace publishing. Local packaging features do not all qualify for public ZIP submission.
14. [Examples](https://developers.openai.com/plugins/build/examples): an index to the Pizzaz MCP/UI examples. It is illustrative and has no normative Scio contract or requirement to add UI. External example repositories were not opened.
15. [Connect and test](https://developers.openai.com/plugins/deploy/connect-chatgpt): test the endpoint first with MCP Inspector, then register it in developer mode and inspect discovered tools. Evaluate direct/indirect/follow-up/negative prompts, invalid input, auth errors, confirmation, and optional UI. Refresh server metadata and rerun cases after changing tools. Install and test the full package after the server works.
16. [Submit and publish](https://developers.openai.com/plugins/deploy/submission): upload ZIP, resolve metadata/skill scan issues, connect and scan one MCP server, serve the exact domain challenge token, then enter review materials. Remote MCP review needs five positive and three negative cases, demo recording, release notes, and private reviewer credentials if OAuth is used. Approval and publication are separate. Public ZIPs with lifecycle hooks or app references are currently excluded.
17. [Submission errors](https://developers.openai.com/plugins/deploy/submission-errors): gives precise metadata, ZIP, image, skill, review, and tool-scan validation codes. Listing text limits include 30-character display/short descriptions and three 128-character starter prompts. Logo and composer icon are mandatory square images. It lists `justification_required`, which conflicts with the newer-sounding guideline in item 26; verify portal behavior.
18. [Restaurant reservation conversion](https://developers.openai.com/plugins/guides/restaurant-reservation-conversion-spec): beta for approved partners, with business feed, required `restaurant_reservation` tool and `ui://widget/restaurant-reservation.html` resource. Input always includes `restaurant_id`; optional business metadata supports initial rendering. Feed needs stable business data, pagination, and change detection. Not relevant to Scio search.
19. [Local services Get Quote conversion](https://developers.openai.com/plugins/guides/local-services-request-quote-conversion-spec): beta for approved partners. A business feed ties a provider action to `request_service`, a fixed widget resource, and `business_id` derived from `provider_business_id`. Quote launcher eligibility depends on complete provider data. Not relevant to Scio search.
20. [Product checkout conversion](https://developers.openai.com/plugins/guides/product-checkout-conversion-spec): beta for approved partners, with `checkout_session` and a fixed checkout widget URI. Item `id` and `quantity` are required; merchant offer metadata is optional and should not be invented. Server retrieves authoritative catalog, inventory, and pricing. Not relevant to Scio search.
21. [UI guidelines](https://developers.openai.com/plugins/concepts/ui-guidelines): use inline cards, carousels, fullscreen, or picture-in-picture only when they improve interaction. Cards should avoid nested navigation and scrolling; carousels serve small visual sets. UI should inherit system fonts/colors, support contrast, alt text, and text resizing. Relevant only if Scio later adds a widget.
22. [Optimize metadata](https://developers.openai.com/plugins/guides/optimize-metadata): build a labeled golden set of direct, indirect, and negative prompts; test precision and recall in developer mode. Descriptions should say when to use a tool and when not to. `openWorldHint` can apply to public search even if the tool is read-only. Change metadata one field at a time and replay tests.
23. [Claude plugin migration](https://developers.openai.com/plugins/guides/submit-claude-plugin): convert reusable commands/agents to skills; Claude `userConfig`, local hooks, live artifacts, `.app.json` references, and local MCP assumptions do not become an ordinary ChatGPT workflow. With MCP submission requires a stable remote HTTPS endpoint and OAuth for private data. The guide notes UserInfo verified-email and `openid`/`email` scope support for workspace domain restrictions.
24. [Security and privacy](https://developers.openai.com/plugins/guides/security-privacy): least privilege, explicit consent, server input validation, prompt-injection defense, redacted logs, retention/deletion rules, and confirmation for irreversible actions. Widget CSP confines fetch and resource origins; nested frames need declaration. Server-side OAuth scope checks and token handling remain necessary.
25. [Troubleshooting](https://developers.openai.com/plugins/deploy/troubleshooting): isolate server, widget, and client failures. Missing tools often means wrong `/mcp` URL or failed initialization; auth loops require checking `WWW-Authenticate`, issuer/audience, and client registration. Proxy buffering can break streaming; metadata changes need refreshed connection and clean conversation.
26. [Plugin guidelines](https://developers.openai.com/plugins/plugin-guidelines): plugins need a clear useful purpose, accurate listing, stable behavior, privacy policy, and user-aligned tool use. They prohibit collecting authentication secrets through plugin interactions, manipulative tool-selection instructions, generic executor tools that hide operations, and unnecessary chat/location/telemetry inputs. The page says annotation justifications are **no longer required**, contradicting item 17. Desktop and mobile testing is expected. Current commerce policy restricts sales through plugins to physical goods.
27. [Remote MCP review](https://developers.openai.com/plugins/deploy/app-review): requires verified publisher identity, Apps Management access, production public endpoint, scan, domain proof, and reviewer-ready experience. The scanned server metadata determines actual tool annotations and schemas; prose cannot override it. Template URLs are limited to trusted developers. Projects with EU data residency currently cannot submit MCP plugins for review. Reviewer login must work without inaccessible MFA or private network.
28. [UI reference](https://developers.openai.com/plugins/reference): exact optional `window.openai` bridge functions, tool descriptor `_meta`, UI resource CSP/domain/display-mode fields, file inputs, and result fields. `structuredContent` and `content` are model-visible; result `_meta` is component-only. It states all three safety hints are required on tool descriptors. New UI should prefer standard MCP Apps fields over compatibility aliases.
29. [Checkout API](https://developers.openai.com/plugins/build/monetization): external checkout is the generally available approach for eligible physical goods; saved merchant payment methods may be used in optional UI. ChatGPT's payment sheet and `requestCheckout`/`complete_checkout` are a limited beta. Prices and orders remain server-authoritative, amounts use minor currency units, and payment completion must be robust and auditable. Not relevant to Scio search.

## Reading cautions

- The [general package guide](https://developers.openai.com/plugins/build/plugins) mentions components usable in local runtimes; the [public submission guide](https://developers.openai.com/plugins/deploy/submission) currently rejects hook/app-reference ZIPs. Apply the submission rule to this public package.
- The [submission error reference](https://developers.openai.com/plugins/deploy/submission-errors) is more exact than introductory examples for field lengths, but conflicts with the [guidelines](https://developers.openai.com/plugins/plugin-guidelines) about annotation justifications. Keep the conflict visible until portal validation settles it.
- The [skill guide](https://developers.openai.com/plugins/build/skills) gives an MCP dependency example in `agents/openai.yaml`, while the [portable package guide](https://developers.openai.com/plugins/build/plugins) says root `skills/` needs no manifest `skills` field. Test the real combined format; do not assume the two examples are interchangeable.
- OpenAI can change these pages. Recheck the linked pages, especially submission, authentication, guidelines, and errors, before altering the package or entering the portal.
